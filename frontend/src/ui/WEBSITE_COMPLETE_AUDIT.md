Audit date: 22 October 2026. Scope: the current local working tree, including existing uncommitted work. This is a source-based functional and architectural audit, not a visual certification. Paths below are relative to `frontend/src/ui/` unless prefixed with `frontend/`. Function/component names identify the relevant code without relying on line numbers that may change.

## 1. Product and implementation status

Legends Field Indoor is a React single-page frontend presenting a football/cricket indoor turf venue in Karachi. Stage 1 combines an editorial homepage with a fictional player community, team management, booking proposals, captain challenges/messages, and sports results.

The UI genuinely performs local state transitions, validates forms, calculates statistics, renders records, and changes themes. Its accounts, bookings, messages, fixtures, and competitive records are demonstrations. There is no backend, secure authentication, database, payment service, venue availability service, notification delivery, or real scoring feed.

Three distinctions are essential:

1. **Booking request:** a local game plan submitted by a selected team's captain. It does not reserve turf.
2. **Challenge:** a proposal between teams, with pending/accepted/rejected/cancelled status. Acceptance does not create a booking or fixture.
3. **Scheduled match:** an explicitly confirmed fictional record generated by `data/matches.jsx`. Only appropriate completed records contribute to statistics.

All community/session data resets on refresh. Only the light/dark preference persists. A user may be captain of one team and an ordinary player on another; captain status is not a separate account type.

## 4. Application architecture and routing

### 4.1 Component hierarchy

```text
public/index.html (#root)
  src/index.jsx: createRoot(...).render(<App />)
    App.jsx
      Website.jsx
        Suspense
          lazy CommunityProvider
            SiteRoutes
              skip link
              Navbar
              Suspense
                AnimatedPage
                  resolved page OR AccountGate OR not-found content
              Footer
```

`CommunityProvider` stays mounted across route changes. Route content is keyed by pathname, query string, and active player ID. Navigation/account switching therefore remounts page-local forms and filters while retaining shared session records. No React Router, Redux, server router, or SSR application framework is used.

### 4.2 Router behavior

`Website.jsx::resolveRoute` checks static routes, account subpages, team management, and dynamic public detail routes. A final trailing slash is normalized. `SiteRoutes` uses `history.pushState` and `popstate`; `data/navigation.jsx::goTo` pushes history and dispatches a popstate event.

An ancestor click handler intercepts ordinary same-origin links to recognized routes. Modified clicks, external links, targets, and downloads use native browser behavior. Same-page hash navigation is left to the browser. Route transitions handle top scrolling or a hash target and focus the main region when no hash is present.

Visitor clicks on an exact `/booking` link are rewritten to `/account?next=%2Fbooking`. Direct visitor loads of protected URLs show `AccountGate` at the requested URL instead. The gate links to account access with a return destination.

`safeNext` accepts selected internal account, booking, team, challenge, and inbox paths. It rejects external and protocol-relative URLs; it is not a complete route-existence validator. Document titles are assigned on route changes.

The development server supports SPA fallback. Production hosting must independently serve the app shell for nested routes while preserving actual asset requests. An unknown route displays a client-side not-found page; this is not an HTTP 404 implementation.

### 4.4 Query parameters, anchors, and local filters

- Account: `mode=access`; allowlisted `next`. `/login` defaults to access; `/register` defaults to creation.
- Management: `tab=Overview`, `Players`, `Join Requests`, `Invitations`, or `Team Settings` initializes the section; spaces must be URL encoded.
- Challenges: `from`, `opponent`, and `challenge`; a challenge ID may also be the hash target. Invalid/unowned `from` falls back to an eligible captain team.
- Inbox: `from` and `thread`; available threads are constrained to the selected captain team.
- Matches: `sport=Cricket`, otherwise Football.
- Rankings/leaderboards: `sport=Cricket`; `period=all`, otherwise current month. Metric selection is local, not a query parameter.
- Homepage anchors: `home`, `about`, `facilities`, `booking`; shared footer: `contact`; challenges: `challenge-activity` and individual challenge IDs.

Most filter, team-selector, and management-section changes do not rewrite the URL. Reloading or leaving/reentering can therefore restore initial query/default selections rather than the last visible selection.

## 5. Visitor, player, and captain journeys

### 5.1 Visitor

A visitor starts with `activePlayerId: null`. They can explore the homepage, directories, profiles, matches, rankings, leaderboards, and rivalries. The main navigation has Home, Book Turf, Teams, Matches, Rankings, Explore, and My Account.

Book Turf through an ordinary in-app link opens account access with a booking return destination. Direct `/booking` loads show a gate before any slot controls. Team creation, account subpages, challenges, inbox, and management also require account access. Public team pages offer an account-entry link when joining is attempted.

Explore contains Players, Player leaderboards, Rivalries, and the theme toggle. Visitors have one main My Account entry rather than separate visible Login/Register navigation.

### 5.2 Account creation and access

Registration in `Account.jsx` has four stages:

1. Name, email, sample password, confirmation.
2. Football and/or cricket; primary football position and optional secondary positions; cricket role.
3. Optional profile image.
4. Review and create.

Name must contain 1–70 trimmed characters; email must pass a basic pattern and be unique among stored session emails. The form requires at least eight password characters and matching confirmation. Passwords exist only in local form state and are removed before dispatch; the reducer does not store or authenticate them.

Successful creation appends a player, immediately sets the active ID, and opens `/account`, retaining a valid `next` as a Continue link. A second login is unnecessary. Existing-account access is a dropdown of all sample and session-created players, without password verification. It activates the selection and navigates directly to `next` or `/account`.

The dashboard shows identity and links rather than every management control. Settings lets the user switch identities or exit. Switching retains the session's players/teams/requests but remounts the current page. Exiting clears active identity and selected inbox conversation, not the entire demo dataset.

### 5.3 Profile, discovery, and membership

My Profile exposes personal information, sport selection, and the collectible card. Edit Profile changes name, sports, positions/role, and photo in the shared player record. Email and bio are not editable there. Removing a sport required by a current team is rejected.

Player discovery searches name/ID and combines sport, football-position, and cricket-role filters. “Both” requires two sports. Team discovery searches team name and filters sport. These are immediate local filters with no server search or pagination.

An eligible nonmember requests to join from a public team profile. Duplicate pending invitations/requests are prevented. The player can cancel their own pending request from the team page, My Teams, or Invitations. Invitations can be accepted/declined from personal pages or the relevant team page. Acceptance immediately adds the player ID to the shared roster.

My Teams separates captain and ordinary memberships. An ordinary member can leave after confirmation. Leaving cancels obsolete pending membership records for that pair and clears a booking draft selecting that team. Historical matches and previous booking requests remain. Captains cannot leave their own team; transfer is not implemented.

### 5.4 Captain workflow

Creating a team sets `captainId` to the active player and initializes `members` with that same ID. No captain signup or global role toggle exists.

The captain enters `/teams/:id/manage` from My Teams, the team page, or creation success:

- **Overview:** identity/counts, team-specific challenge/inbox links, own-team booking preselection, submitted team booking requests, public team link.
- **Players:** current roster and positions; remove eligible members through confirmation; search eligible registered nonmembers by name, ID, position/role; invite.
- **Join Requests:** pending and historical entries; approve or reject pending requests.
- **Invitations:** pending/history; cancel pending invitations.
- **Team Settings:** edit name/logo/description. Sport, captain, and members are preserved.

Removing another player updates the same shared roster and cleanup rules as leaving. The captain cannot remove themselves. Team names are normalized for duplicate checking within the same sport, require 2–50 trimmed characters, and descriptions are limited to 280 characters.

Invitations are demonstrated by switching to the recipient account, accepting, and switching back. Messages and challenge responses likewise require switching to the other captain in the same local session; nothing reaches another device or person.

## 6. Booking system in detail

Sources: `pages/Booking.jsx`, `state/accountActions.jsx::bookingErrors`, `state/communityReducer.jsx`, `data/booking.jsx`, `components/BookingRecord.jsx`.

### 6.1 Guided steps

1. **Sport:** Football or Cricket. Both buttons are visible, but continuing requires the sport on the active profile. Changing sport clears team/opponent selection.
2. **Date and slot:** defaults to tomorrow in Asia/Karachi. Five quick dates and a native date input are available; the latter allows later dates. Changing date clears the slot.
3. **My Team:** lists same-sport teams containing the player. Inline creation asks name and optional logo, uses the same team reducer, makes the player captain, and selects the new team. A team-directory detour retains shared draft values.
4. **Opponent:** searchable existing same-sport teams, excluding the selected own team. There is no opponent-creation control. Another team captained by the same account is not specifically prohibited.
5. **Review:** player, sport, date, time, duration, teams, venue, demo status, and unrequested opponent confirmation; links can return to earlier steps.
6. **Result:** after submission, shows the local request ID and details, My Bookings link, and a separate challenge link for the team pair.

### 6.2 Availability and permissions

Every demo slot is 60 minutes. Start times are 10:00, 11:00, 12:00, 14:00, 15:00, 16:00, 18:00, and 19:00. They are grouped as morning/afternoon/evening. These are illustrative, not confirmed venue hours.

`slotsForDate` converts the date to a numeric seed and marks a slot available when `(seed + index) % 4 !== 0`. Availability does not depend on real bookings, sport, opponent agreement, or a backend. Requests do not consume slots.

A member may browse and select a team but cannot submit unless they captain that team. The form explains this at own-team selection/review, links to the captain's public profile, and disables final submission. The reducer repeats the captain check independently.

### 6.3 Validation and records

Validation requires an active player, registered sport, real calendar date no earlier than tomorrow in Karachi, an available listed slot, same-sport own membership, own-team captain authority, and a different existing same-sport opponent. It rejects a second request by the same player for the same date/start time, regardless of team or sport.

Drafts are stored as `bookingDrafts[playerId]` and merged on edits. They survive route navigation/account switching in the same mounted session, but the current wizard step is local and resets on remount.

Submitted records contain `id`, `playerId`, `sport`, `date`, `slot`, `teamId`, `opponentId`, `duration: 60`, `status: 'Demo request'`, `opponentStatus: 'Not requested'`, and ISO `createdAt`. IDs use `demo-booking-${sequence}`. Submission clears that player's draft.

My Bookings filters by submitter ID. Captain overview filters by the request's own `teamId`; opponent selections do not become accepted participation records. Details resolve current team/player names through shared IDs. Refresh removes requests and custom entities.

### 6.4 Boundaries and confusing behavior

There is no cancellation/edit lifecycle for submitted requests, actual reservation, price, payment, booking approval, opponent notification, or cross-user slot conflict prevention. Duplicate prevention is per submitter, not venue-wide. These are demo limits, not evidence of failed real booking integration.

The booking-to-challenge link passes only team IDs. Date/time are not prefilled, and there is no booking/challenge foreign-key relationship. Challenges can propose any valid future Karachi time, including later today, whereas booking begins tomorrow and only offers the eight listed starts. “Contact your captain” links to a public profile, not a member-to-captain contact mechanism.

## 7. Shared data, state, and permissions

### 7.1 State model

`CommunityStore.jsx` defines the context/hook. `CommunityContext.jsx` owns one `useReducer` and derives `activePlayer` by ID. `communityReducer.jsx::initialCommunity` initializes:

- `players`, `teams`, `activePlayerId`;
- `bookings`, per-player `bookingDrafts`;
- `invitations`, `requests`;
- `challenges`, `conversations`, `inboxConversationId`, `rivalries`;
- generated `matches`;
- shared `sequence`, `notice`, and `noticeKind`.

Context exposes all state plus `dispatch`. It does not provide separate per-feature providers or memoized selectors. Most pages call array filters/finds directly. This is manageable for the small sample but broad updates can rerender many consumers.

### 7.2 Entity schemas and initial identities

Players contain `id`, `name`, `photo`, `sports`, `positions`, `role`, and `bio`; created players also contain `email`. `positions[0]` is primary. Photo is a bundled URL or local data URL. New players use `demo-player-${sequence}` and a default bio. IDs are session identifiers, not verified identity numbers or permanent database IDs.

The six seed players are Ayaan Malik (`demo-p001`), Zain Ahmed (`demo-p002`), Saad Khan (`demo-p003`), Imran Shah (`demo-p004`), Bilal Raza (`demo-p005`), and Hamza Ali (`demo-p006`).

The four seed teams are:

- Harbour Athletic, `demo-harbour`, Football, captain Ayaan; members Ayaan/Saad.
- Creek Cricket Club, `demo-creek`, Cricket, captain Zain; members Zain/Ayaan.
- Coast United, `demo-coast`, Football, captain Imran; members Imran/Bilal.
- Falcons Cricket, `demo-falcons`, Cricket, captain Bilal; members Bilal/Saad.

Teams contain `id`, `name`, `sport`, `captainId`, `members`, `logo`, and `description`. There are no separate roster objects. A player can belong to multiple teams, including multiple teams in one sport; roster capacity is not enforced.

Football positions: Goalkeeper, Defender, Midfielder, Forward. Cricket roles: Batsman, Bowler, All-rounder, Wicketkeeper. There are no numeric overall ratings.

Membership entries contain ID, team ID, player ID, and status. The seed includes an invitation for Ayaan to Coast and a request for Imran to Harbour. Conversations contain a two-team ID list and message records with sender-team ID, text, timestamp, and ID. Rivalries define fixed team pair identities and labels; their totals are calculated.

### 7.3 Reducer action inventory

| Actions | Actual effect and boundary |
|---|---|
| `clearNotice` | Clears global feedback. |
| `createAccount` | Validates profile/email, adds sanitized player, activates it, increments sequence. |
| `switchPlayer`, `exitAccount` | Select valid local identity or clear active identity; no authentication. |
| `editProfile` | Updates whitelisted fields on the active player; prevents incompatible removal of current team sports. |
| `bookingDraft`, `createBooking` | Merge player draft; validate and append demo request; clear draft. |
| `createTeam`, `editTeam` | Create captain/roster together; specific captain can update identity fields. |
| `invite`, `request` | Validate existing sport-eligible nonmember and no pending duplicate across either membership collection. |
| `respondInvite`, `cancelInvite` | Recipient accepts/rejects; team captain cancels pending invitation. Acceptance updates roster. |
| `respondRequest`, `cancelRequest` | Captain approves/rejects; requester cancels own pending request. |
| `leaveTeam`, `removeMember` | Own ordinary membership departure or captain removal of another member; cleanup pending entries/draft. |
| `sendChallenge`, `respondChallenge`, `cancelChallenge` | Delegated competition validation/transitions; no fixture/reservation mutation. |
| `openConversation`, `sendMessage` | Validate captain/team pair, reuse/create thread, append local text. |

All post-account membership/booking/competition mutations require an actor. Captain actions compare `actor.id` with the relevant team's `captainId`. Receiving an invitation requires the matching player. Approving requests requires that team's captain. This guards normal frontend transitions; it does not secure data against a user controlling the browser.

### 7.4 Synchronization and persistence

Names, photos, memberships, and team settings propagate because pages resolve the same shared records. Booking/challenge/message references store IDs, so renaming a team updates displayed names in existing records. Historical match lineups are separate snapshots, not live rosters. Leaving a team does not erase appearances or rewrite results.

Community data is held only in React memory. There is no sessionStorage use and no community persistence in localStorage. Refresh, a new tab, or a full document navigation starts a new demo session. A custom ID copied into a new tab may therefore be missing.

The shared sequence supplies IDs across entity types. Several forms predict the next ID using the rendered sequence; this works in the current synchronous UI but should not be carried unchanged into asynchronous backend integration.

## 8. Player cards and images

`PlayerCard` supplies directory cards using the first registered sport and first matching current team. `CollectibleFace` renders front/back HTML. Public and personal profiles use `PlayerCardExperience`, defaulting to lightweight 2D.

“Flip card” changes side. “Explore in 3D” first checks WebGL2 with `failIfMajorPerformanceCaveat`, then lazily imports `PlayerCardScene`. Reduced-motion preference prevents 3D activation and returns an active scene to 2D. A scene error boundary, Suspense fallback, unsupported-context handling, and context-loss callback preserve the 2D presentation.

The scene uses React Three Fiber `Canvas`, Drei `useTexture`, and Three.js geometry/materials. It builds 560×820 canvas textures from player information and portrait, maps them to a shield-shaped extruded card, and uses a fixed camera plus ambient/directional lights. Pointer movement gently tilts; touch movement is ignored for tilt and vertical scrolling is permitted. Flip animates rotation. `frameloop="demand"`, bounded DPR `[1, 1.5]`, low-power preference, and interpolation that stops requesting frames after settling limit work. Generated front/back textures are disposed on replacement/unmount.

The 3D artwork deliberately retains dark green card colors in both website themes. It is not a second theme stylesheet. The canvas is hidden from accessibility APIs; HTML descriptive text and regular buttons carry identity and controls. GPU correctness and context-loss recovery have not been browser-tested in this audit.

`ImageUpload` accepts JPEG/PNG/WebP up to 2 MiB, decodes with FileReader/Image, downsamples the longest side to at most 400 pixels, and stores a PNG data URL in session state. Invalid/pending uploads block relevant form submission; a version counter prevents stale callbacks applying after reset/unmount. No file leaves the browser through this component.

The turf image is illustrative, not verified venue photography. `assets/README.md` explicitly says its redistribution license has not been verified. Portrait documentation identifies Random User Generator images as fictional-profile illustrations. These provenance notes are local documentation claims; no external license audit was performed.

## 9. Matches, statistics, rankings, and rivalries

### 9.1 Fixture generation and sources of truth

`createDemoMatches` initializes records once per provider session. Fixtures contain ID, sport, team IDs, date/time, status, `confirmed: true`, venue, and historical lineup snapshots, plus football/cricket data where relevant.

The sample combines fixed July–September 2026 completed fixtures, current-month examples, current live/interrupted snapshots, and future Upcoming/Postponed/Cancelled examples. Completion-time filtering prevents completed examples appearing before their generated completion time. Counts therefore depend on date/time; records are not real venue schedules.

Mock input values are scripted. Derived displays are calculated from those inputs. No action in the app records a goal, edits a score, starts a real match, or converts a proposal into a fixture.

### 9.2 Football

Football details show team logos/names, score, simulated/frozen clock, goal/assist/card/substitution timeline, and historical lineup links. Completed goals and events are generated to match scripted score totals. Demonstration format is two 20-minute halves, not a statement of venue rules.

The live clock derives elapsed time from a mock timestamp and caps at 20:00. Half-time freezes at 20:00; completed records show 40:00. Clock progression does not change score/status or trigger a second half. `matchClock.jsx` shares one one-second interval across subscribers, skips updates while the document is hidden, and removes the interval when unused.

Player football metrics are completed appearances, counted goal events, counted assist IDs, and clean sheets when the fixture identifies the player as goalkeeper and the side conceded zero. Goalkeeper IDs are historical fixture data; current-position edits do not alter `playerRecord` credit. However, current profile role still controls whether clean sheets are shown/ranked, discussed in findings.

### 9.3 Cricket

Cricket details show runs/wickets, overs, current innings, target, current run rate, required rate for eligible live chases, batting/bowling teams, selectable innings, batting and bowling tables, and every scripted delivery.

`buildInnings` replays a deterministic delivery script to derive aggregate and player/bowler totals. A wide contributes an extra and bowler run without a legal ball or batter ball. Six legal balls form an over: 28 balls displays as `4.4`, not a decimal fraction. The demo limit is 60 legal balls and six wickets. Historical guest batters have labels but no registered player IDs and are not ranked.

Results compare innings totals; a successful chase uses wickets remaining, a defended total uses run difference, equal scores tie, and explicit no-play fixtures return no result. Live cricket is a static scorecard snapshot, not an advancing ball feed.

### 9.4 Statistics and eligibility

`completedMatches` requires confirmed, Completed fixtures and optionally the Karachi calendar-month prefix. `appearances` uses historical lineups; cricket with no innings contributes no player appearances.

Cricket totals aggregate runs, balls, boundaries, wickets, legal bowling balls, and conceded runs. Batting strike rate = runs × 100 / balls faced; bowling economy = conceded runs × 6 / legal balls. Zero denominators produce no rate rather than an invented zero.

`leaderboard` starts with registered players currently listing the selected sport and with completed appearances. Football offers goals, assists, appearances, and clean sheets; the latter additionally requires current Goalkeeper position. Cricket offers runs, wickets, strike rate (minimum 20 balls), and economy (minimum 12 legal bowling balls). Batting/bowling participation is required for the relevant count metrics. Economy sorts ascending; other metrics descending. Unrounded values decide ordering; displayed rates have two decimals. Equal metric values share competition rank, with names sorting tied display rows.

Profiles, ranking tables, and rivalry totals use shared selectors rather than separate manually maintained totals. `MatchHistory` displays only the latest six supplied matches, then links to the general match center.

### 9.5 Team standings and periods

Football: win 3, draw 1, loss 0. Columns include played/won/drawn/lost, goals for/against/difference, points. Order: points, goal difference, goals scored, team name.

Cricket: win 2, tie 1, no result 1, loss 0. Order: points, wins, team name. No football metrics or net run rate are used. New teams appear with zero completed results. Team positions are sequential even where competitive values tie; player leaderboards use shared ranks.

Current Month filters by `Asia/Karachi` month; All-Time uses all available completed sample history. There is no historical-month picker, scheduled deletion/reset, or archival database. The “monthly spotlight” is explanatory promotional UI with no real prize or reward logic.

### 9.6 Rivalries

The registry defines Harbour–Coast and Creek–Falcons. `rivalryMatches`, `rivalryHistory`, and `rivalrySummary` calculate meetings, winners, scores, and distribution from completed confirmed shared fixtures; no-result games are excluded. Cards show recent meetings, and detail pages link to corresponding match records. New challenges do not add rivalries or results automatically.

## 10. Challenges and captain messaging

Challenges operate under one selected captain-managed team. The page restricts the source list to the active player's captain teams, chooses that team's sport, filters its activity, and passes a locked source team to the guided form. Repeated controls show incoming/outgoing and pending/accepted/rejected/cancelled status.

The form stages are My Team, Opponent, Date & time, Message, Send/review. Validation requires captain authority, two different existing same-sport teams, a valid future Karachi schedule, message at most 500 trimmed characters, and no pending/accepted challenge for the same unordered pair/sport/date/time. It does not check venue slots or other-team schedule conflicts.

Only the receiving captain accepts/rejects a pending proposal; only the source captain cancels. Acceptance of an expired schedule is rejected. Accepted proposals have no implemented cancellation or booking-conversion workflow. `ChallengeCard` additionally scopes visible actions to the selected team, avoiding mixed sender/receiver controls when the user captains both teams.

Inbox lists threads involving the selected captain team. Opening a conversation validates a different same-sport opponent and reuses the existing unordered pair thread when present. Messages contain sender team, text, and timestamp; 1–1,000 trimmed characters are required. Messages are inserted locally, never delivered. There are no attachments, unread counts, read receipts, notifications, or individual-player chat.

The conversation displays current opponent/captain identity, explicit writing-as team, recent related proposals, and a polite live log. Thread lists sort by latest message timestamp. Switching team resets local selection/mobile conversation state; switching account remounts the page. Small-screen list/conversation toggling uses CSS and a Back button. Related challenge links preserve team context.

## 11. Design system, responsiveness, and accessibility

### 11.1 Visual language and CSS architecture

The visual direction is off-white/light surfaces or dark charcoal-green, restrained turf-green accents, generous rounded panels, large headings, photographic hero, shield-shaped player cards, and dark sports scoreboards. This description follows the CSS and markup, not a fresh screenshot inspection.

Shared final light tokens in `refinement.css`: ink `#202824`, paper `#f7f6f1`, green `#b8d99b`, muted `#58635c`, line `#dce1d8`, surface `#fffefa`, radius 20px. Dark tokens in `theme.css`: ink `#edf1e9`, paper `#141c17`, muted `#b8c6b8`, line `#405344`, surface `#1d2921`, green `#b8d99b`, plus semantic surface/text/focus/error/warning tokens.

The final shared body font is Segoe UI with Arial/sans-serif fallbacks, usually 17px. Controls commonly use 16px, helpers 14px, and eyebrows 13px. Main headings use clamped sizing; shared h1 is 40–78px, with a 60–110px homepage override. Card edition/ID microcopy still includes 11–12px sizes. Some older component-specific Arial declarations remain.

Styles are global, not CSS modules. `home.css` supplies reset/shell; `home-page.css` homepage sections; `navigation.css` navigation; `polish.css` motion; `phase2.css` forms; `community.css` cards/profiles/teams and imports phase2; `competition.css` challenges/inbox/rivalries; `sports.css` scores/tables; `refinement.css` shared overrides; `workspaces.css` account/management/dialog layouts; `theme.css` theme tokens and state overrides.

`PageHeader` also imports phase2 CSS. Route CSS is injected by style-loader when modules load and is globally applicable. Specificity such as `body .…` and `html[data-theme=dark] body …` helps overrides survive, but cascade/order interactions still need browser checks.

### 11.2 Theme system

`theme.jsx` uses a module-level external store and `useSyncExternalStore`. Before React renders, it reads `legends-field-theme` from localStorage. Valid saved light/dark values win; otherwise the OS preference decides. It sets `document.documentElement.dataset.theme` and `style.colorScheme`, tracks system changes while no explicit preference exists, and handles storage events across tabs.

The toggle is text-labelled in Explore and Account Settings. It stores an explicit choice; if storage fails, the tab still changes theme. Existing light colors remain CSS variable fallbacks; dark mode supplies semantic replacements and selected/disabled/focus/status overrides. There is no UI to clear an explicit choice and resume automatic system following.

Initialization precedes the React UI, but `public/index.html` has no pre-script theme bootstrap/background. A blank wrong-color frame before JavaScript execution is therefore not ruled out by the implementation or tests.

### 11.3 Navigation and responsive behavior

The header is sticky, adds a scrolled class after 20px, and has an Explore disclosure plus account/avatar link. Escape closes Explore first, then mobile navigation; outside pointerdown closes menus. Link clicks close navigation. The mobile menu becomes active at 1280px, with an 80px header adjustment at 700px.

Stylesheet breakpoint inventory:

- Home/shell: 1000, 700px.
- Navigation: 1280, 700px.
- Phase 2 forms: 1100, 900, 700px.
- Community: 1180, 900, 700, 500px, plus a 501–700px range.
- Competition: 1100, 900, 700px.
- Sports: 1000, 750, 400px.
- Shared refinement: 1180, 900, 600px.
- Workspaces: 680px.

Account/booking columns collapse around 900px, workspace cards at 680px, and player/slot/podium layouts receive narrow-screen changes at 600px. Sports tables use focusable horizontal-scroll regions, with minimum widths of 600px and 850px for standings. Progress lists scroll horizontally. Long names receive wrapping in many important components. These are code provisions, not proof of overflow-free rendering on every device.

### 11.4 Motion and accessibility

`AnimatedPage` uses IntersectionObserver for headings/cards/sections with threshold 0.08 and restrained stagger. CSS provides upward fades, sideways copy, clipped image reveals, word-staggered hero text, hover lifts/zoom, and a short page entrance. Elements remain visible until finite animations begin, so missing observers do not permanently hide content. The observer scans elements when the route mounts; later tab/filter-added content is not automatically rescanned.

Reduced-motion CSS disables animations/transitions; JS skips observers and forces the 3D card into 2D. Match clocks use `aria-live="off"`; message history uses a polite log. Other provisions include skip-to-main, route/step heading focus, labelled controls, error associations and focused summaries, pressed/selected states, semantic tables/captions, native radio/checkbox inputs, accessible card text, and keyboard-operated public profile sport tabs.

`ConfirmDialog` uses native `showModal`, focuses the safer cancellation button, handles Escape via `onCancel`, and tries to restore prior focus. Its unsupported-dialog fallback only sets `open`; it does not implement a custom focus trap/inert background. Actual keyboard/screen-reader behavior remains to be tested.

## 13. Confirmed gaps and source-supported concerns

The following are not claims of browser reproduction. “Confirmed” means the relevant control/state logic is directly present in source. No fixes were made during this audit.

### 13.1 Confirmed interaction and workflow gaps

1. **Registration can remain blocked after leaving an invalid upload step.** `Account.jsx` keeps `blocked` at page level, disables Continue at every step, and permits Back without clearing it. `ImageUpload` clears its parent status only through its own reset/upload paths. Invalid file → Back from photo step leaves the user on an earlier step with Continue disabled and no mounted upload control to clear the error. Reloading or a navigation remount resets the form but loses progress. Prioritize this recovery path.
2. **Inline booking upload cancellation retains the parent block flag.** `Booking.jsx` toggles `creating` without resetting `imageBlocked`. Cancelling after an invalid logo and reopening mounts a fresh upload control but leaves Create disabled; a new valid upload/reset interaction is needed. The newly mounted empty control has no visible Remove action until an upload/error exists.
3. **Personal fixture filtering is broader than its surrounding wording.** `AccountPages` uses `status !== 'Completed'`, so cancelled/postponed records appear with current fixtures. Its sport selector filters recorded appearances/statistics, not the current-team fixture list. The empty text refers to “upcoming” despite broader selection.
4. **Personal/team history is silently limited to six entries.** `CommunityElements::MatchHistory` slices to six without a Show All personal-history control. Its general match-center destination loses the original player/team filter.
5. **Booking/challenge handoff loses schedule context.** Only `from` and `opponent` are passed. The user reenters schedule details, and same-day/arbitrary-time challenges may not be representable in the booking wizard. There is no record link or reconciliation step.
6. **Footer labels do not name their immediate destination.** “Challenges” and “Captain Inbox” both navigate to `/account/teams`, intentionally requiring team selection but without saying so. `/matches` still exposes a global challenge link, while main navigation routes captain work through teams.
7. **Captain contact guidance has no contact action.** Booking links ordinary members to the captain's public profile, which has no member messaging/contact control. The explanation is useful, but the suggested contact workflow ends there.
8. **Theme cannot return to automatic mode through UI.** After a toggle, a saved explicit preference overrides future system changes until storage is cleared externally.
9. **Current role/sport changes can hide historical leaderboard participation.** Historical `playerRecord` clean sheets remain intact, but `profileStatistics` conditionally shows them only for current goalkeepers; leaderboard eligibility also uses current positions/sports. Removing a sport is allowed after leaving its teams, potentially removing that player from historical leaderboards despite preserved fixture records. This is a policy ambiguity, not corrupted match data.
10. **Pending memberships are not reconciled on sport edits.** Profile validation protects current team sports, not sports referenced only by pending invitations/requests. Removing such a sport leaves a pending item visible; acceptance is correctly rejected as ineligible, but the item stays pending until cancelled/rejected or the sport is restored.
11. **Submit feedback and predicted IDs assume synchronous local success.** Booking/team/conversation forms predict IDs from `sequence`; challenge form marks sent after dispatch. Current form/reducer checks largely agree, but these patterns need an explicit success/error result when asynchronous operations are introduced. A time-sensitive validation boundary can also change between form and reducer evaluation.

### 13.2 Confirmed maintenance and product limits

- `data/player.jsx::validateLogin` and `validatePlayer` are unused legacy validators; active forms use `accountActions`. `Login.jsx`/`Register.jsx` are compatibility reexports, while `Website` aliases Account directly. They are not separate active login implementations.
- Starter `App.css`/`index.css` are unimported. Older auth/management selectors remain in phase2/community styles alongside current workspace styles.
- JSX is often compressed into long lines and CSS depends on multiple global override layers. This makes review, visual regression diagnosis, and safe changes harder.
- Account access has a password-shaped creation form but no password-based access. The demo explains this, yet first-time users may still expect secure credentials.
- No lists use pagination/virtualization. Cricket details render an entire delivery timeline; large future datasets would require different rendering/data-loading strategies.
- `npm test` is a placeholder that exits with failure; the real verification script must be run explicitly.
- Earlier documentation is historical: `STAGE1_REFINEMENT.md` describes an older dashboard/navigation and 72 renders; `PHASE5.md` reports an earlier smaller entry. Current source and this audit supersede those status details.
- Fixed historical fixtures are dated in 2026; current-month examples regenerate relative to initialization. This is illustrative data, not durable sports history.
- No team deletion/transfer, account deletion, password reset, email verification, submitted-request cancellation, or real booking lifecycle exists. These omissions must not be presented as completed production features.

### 13.3 Potential issues requiring browser or targeted runtime testing

- Initial theme flash before script execution; contrast of every selected/hover/disabled state in both modes.
- Lazy global CSS order after navigating different route sequences, especially reused component selectors.
- Long names/IDs, 320px layouts, large text/zoom, card clipping, sidebar sizing, progress strips, and horizontal overflow.
- Native dialog focus restoration after the trigger is removed from the roster; unsupported-dialog fallback lacks equivalent modal semantics.
- Mobile menu keyboard reachability and behavior after resize; current implementation is a disclosure, not a full dialog/focus-trapped drawer.
- Error-summary/step/main focus interactions and challenge opponent-browser focus timing. The browser handler tries to focus an opponent field before React may have mounted that wizard step.
- Optional 3D portrait decoding, texture/geometry lifecycle, context loss, touch scrolling, and sustained device performance.
- Scroll-observer coverage after dynamic filter/tab changes, since observation is route-mount based.
- Long-open sessions crossing midnight/month boundaries: fixtures initialize once, while current date/month helpers run later during renders. Refresh creates a new demo dataset.

No frontend captain-permission bypass was found in the inspected normal mutation paths, and the current tests exercise representative unauthorized calls. This is not a security guarantee: all data and identity selection remain browser-controlled.

Run from repository root with `npm --prefix frontend run build` or `npm --prefix frontend start`; Windows may use `npm.cmd`. Run the actual checks with `node frontend/src/ui/verify-refinement.cjs`. Its optional `--http=http://localhost:3001` requires a separately running dev server.

### 14.2 Build setup and loading

Webpack uses `src/index.jsx`, Babel env/react presets, JS/JSX resolution, and style-loader/css-loader. It emits content-hashed entry/chunk/image filenames under `dist`, uses root `publicPath: '/'`, a separate runtime, deterministic IDs, and HtmlWebpackPlugin. `output.clean` cleans build output during normal builds. Dev server defaults to port 3000, HMR, and history fallback.

All route components and the community implementation are lazy-loaded. The shell/context interface remains eager. The community provider still has to load before the initial route shell renders, so the initial entry total is not total first-page transfer. Page CSS is injected from JavaScript; there is no extracted production CSS pipeline or CSS minifier configured.

SplitChunks uses all chunks, 20,000-byte minimum and 200,000-byte target maximum, with React and asynchronous Three.js cache groups. The optional 3D module is requested only after user activation and capability checks. A large indivisible module can exceed the splitting target.

### 14.3 Current warnings

The verified production compile emits two warning categories:

- **Entrypoint size:** approximately 251 KiB, above Webpack's 244 KiB advisory threshold. Runtime plus React vendor chunks account for roughly 218 KiB, and the main bundle about 33.6 KiB.
- **Asset size:** asynchronous Three.js chunks approximately 362 KiB and 371 KiB. Webpack identifies large `three.module.js` and `three.core.js` modules as their dominant inputs.

These are uncompressed emitted sizes, not measured network transfer, load time, or FPS. No warning thresholds were changed or suppressed. Lazy loading, demand rendering, DPR limits, local images, and a default 2D card reduce unnecessary work but do not prove mobile performance.

## 15. Backend integration readiness and safe modification guidance

The frontend has useful domain boundaries: ID-based entities, centralized reducers/validators, separate historical fixtures, and shared statistical selectors. It does not yet have a service layer, API contracts, request lifecycle/cache, durable IDs, migrations, server authorization, upload storage, or live event transport.

Future integration would need server-authoritative identity/captain membership, persistence, real venue availability and atomic conflict checks, booking lifecycle/payment policy, opponent coordination, validated scoring/event ingestion, historical eligibility policy, and reliable error/loading/retry behavior. These are future requirements only; this audit does not start Stage 2.

Rules for modifying this frontend safely:

1. Keep one current-roster source; do not add parallel team membership arrays to pages.
2. Preserve team-specific captain checks in both UI and mutation handling.
3. Keep proposal, request, and confirmed fixture concepts separate until an explicit conversion workflow exists.
4. Preserve historical lineup/goalkeeper snapshots when current profiles or rosters change.
5. Calculate displayed statistics from shared fixtures/selectors, not copied profile totals.
6. Return explicit mutation results before replacing the synchronous reducer with asynchronous calls.
7. Preserve the approved homepage content/layout and test global CSS changes against it.
8. Update `resolveRoute`, guards, allowed return destinations, links, and verification together when adding/changing routes.
9. Test account switching and leaving/reentering routes; page-local state resets intentionally while shared drafts/records remain.
10. Treat theme as the only currently persistent preference; do not imply durable account data.
